# Expense Tracker

A full-stack Expense Tracker application built as part of the Dalil Academy Full Stack Web Development project.

The application uses PostgreSQL, an Express.js REST API, and a responsive Bootstrap frontend. It supports full CRUD operations and includes Search, Category Filter, a category Chart, Dark Mode, and CSV Export.

---

## Features

### Core Features

- View all expenses from PostgreSQL
- Add, edit, and delete expenses
- Filter expenses by category
- Search by title or category
- Summary cards:
  - Total Amount
  - Number of Expenses
  - Highest Expense
- Loading spinner during API requests
- Bootstrap success/error alerts
- Frontend and backend validation
- Responsive layout
- Bootstrap Edit Expense modal

### Bonus Features

- 📊 Expenses by Category chart using Chart.js
- 🌙 Light/Dark mode with saved theme preference
- 📄 CSV export
- 🔎 Search by title or category

## Database

The project uses PostgreSQL.

Database name:

```text
expense_tracker
```

The `expenses` table contains:

| Field | Description |
|---|---|
| `id` | Unique expense ID |
| `title` | Expense title |
| `amount` | Expense amount |
| `category` | Expense category |
| `date` | Expense date |

### Allowed Categories

- Food
- Transport
- Bills
- Entertainment
- Other

The `id` is generated by the database.

## Backend Setup

### 1. Create the Database

Create a PostgreSQL database named:

```text
expense_tracker
```

### 2. Run the Database Schema

Open the PostgreSQL Query Tool for the `expense_tracker` database and run:

```text
backend/schema.sql
```

The schema creates the `expenses` table and inserts the sample expense data.

### 3. Configure Environment Variables

Create a `.env` file inside the `backend` folder:

```env
DB_USER=postgres
DB_HOST=localhost
DB_NAME=expense_tracker
DB_PASSWORD=YOUR_PASSWORD
DB_PORT=5432
```

Replace `YOUR_PASSWORD` with your local PostgreSQL password.

### 4. Install Dependencies

Open a terminal inside the `backend` folder:

```bash
npm install
```

### 5. Start the Backend

```bash
node server.js
```

The server runs on:

```text
http://localhost:3000
```

## API Endpoints

Base URL:

```text
http://localhost:3000/api/expenses
```

### GET — All Expenses

```http
GET /api/expenses
```

Returns all expenses from PostgreSQL.

Example response:

```json
[
  {
    "id": 1,
    "title": "Lunch",
    "amount": 4.5,
    "category": "Food",
    "date": "2026-01-15"
  }
]
```

### GET — One Expense

```http
GET /api/expenses/:id
```

Example:

```text
GET /api/expenses/1
```

Returns the expense with the specified ID.

If the expense does not exist:

```json
{
  "message": "Expense not found"
}
```

### POST — Create an Expense

```http
POST /api/expenses
```

Example request body:

```json
{
  "title": "Coffee",
  "amount": 3.5,
  "category": "Food",
  "date": "2026-02-10"
}
```

A successful request returns the newly created expense with status `201`.

### PUT — Update an Expense

```http
PUT /api/expenses/:id
```

Example:

```text
PUT /api/expenses/1
```

Example request body:

```json
{
  "title": "Updated Lunch",
  "amount": 7.5,
  "category": "Food",
  "date": "2026-02-11"
}
```

The endpoint updates the existing expense and returns the updated record.

### DELETE — Delete an Expense

```http
DELETE /api/expenses/:id
```

Example:

```text
DELETE /api/expenses/1
```

A successful request deletes the selected expense and returns a success message.

## Validation

The API validates expense data before inserting or updating records.

Validation rules include:

- `title` is required
- `title` cannot be empty
- `amount` must be a number
- `amount` must be greater than `0`
- `category` must be one of the allowed categories
- `date` is required
- `date` must be valid
- Invalid or non-existing expense IDs return `404`
- Invalid input returns `400`

The frontend also validates Add and Edit forms before sending requests.

## Frontend Functionality

### Add Expense

Users can add an expense using:

- Title
- Amount
- Category
- Date

The form validates the input and sends a `POST` request to the backend.

### Edit Expense

Clicking **Edit** opens a Bootstrap modal containing the existing expense data.

After saving, a `PUT` request is sent and the page refreshes from the server.

### Delete Expense

Clicking **Delete** asks for confirmation before sending a `DELETE` request.

After deletion, the application reloads the latest data from the server.

### Search and Filter

Users can:

- Search by expense title
- Search by category
- Filter by category
- Combine search and category filtering

The summary cards and chart update according to the currently displayed results.

### Summary Cards

The dashboard displays:

- Total Amount
- Number of Expenses
- Highest Expense

### Chart

The dashboard includes a doughnut chart showing total expenses by category.

The chart updates when the displayed expense list changes.

### Dark Mode

The application supports Light and Dark modes.

The selected theme is stored using `localStorage`, so the choice remains after refreshing the page.

### CSV Export

The **Export CSV** button downloads the currently displayed expenses as:

```text
expenses.csv
```

If Search or Category Filter is active, the exported CSV contains the filtered results.

## Hardest Thing & Solution

### Hardest Thing

One of the more challenging parts was keeping the frontend synchronized with the real backend and PostgreSQL database after Add, Edit, and Delete operations.

Another challenge was making Search, Category Filter, Summary Cards, Chart, and CSV Export work together using the same filtered data.

### Solution

The frontend uses a central `refresh()` flow. After an Add, Edit, or Delete request succeeds, the application fetches the latest data from the server instead of manually changing the table.

```text
API request
    ↓
Server updates PostgreSQL
    ↓
refresh()
    ↓
GET latest expenses
    ↓
Render table
    ↓
Render summary
    ↓
Render chart
```

Search and Filter create a filtered list that is reused for the table, summary cards, chart, and CSV export.

This keeps the displayed information synchronized with the server and makes the frontend behavior easier to maintain.
